# BTX2 — design specification (draft 2026-06-02)

*Successor to BTX1 (the format proven on Bitcoin mainnet in block 952071 on
2026-06-02 — see `BTX-B4-retrospective-2026-06-02.md` for the empirical
record). BTX1 carries one maker order per envelope under a fixed-policy
spot-trade construction. BTX2 extends BTX1 with three capabilities, each
backed by a primitive implemented in this repo as of commit `99e9595`:*

  - **Maker pools** via BIP327 MuSig2 KeyAgg → `btx_musig2.py`
  - **Conditional / oracle-attested orders** via Schnorr adaptor signatures → `btx_adaptor.py`
  - **Multi-maker batch announces** via Schnorr half-aggregation → `btx_halfagg.py`

The companion file `btx_artifact_v2_demo.py` exercises all three together
in a working prototype and reports measured byte savings; this document is
the formal spec the prototype implements against.

This is a **draft**. It captures the intended architecture and is ready to
implement against. It is NOT yet frozen: the field order in record bodies
may shift before a real BTX2 mainnet broadcast. Reviewers and implementers
should treat the binary layout as load-bearing only after the version byte
is bumped past `0x02` and a B4-style mainnet broadcast confirms the format.

## 1. Goals and non-goals

**Goals.**

- Same wire-level shape as BTX1 — a single envelope of artifact bytes carried
  on-chain via OP_RETURN or Taproot witness, decoded by the indexer.
- Three new on-chain-distinguishable record types (single, batch, conditional)
  inside a unified envelope.
- All three new capabilities verifiable from chain data alone, with the same
  "no relay, no escrow, no off-chain channel" properties BTX1 guarantees.
- Backward compatibility at the indexer level: a BTX2-aware indexer continues
  to read BTX1 envelopes as before.

**Non-goals.**

- New consensus rules. BTX2 lives entirely in carrier bytes; Bitcoin Core
  has no idea BTX exists.
- New economic mechanisms. Pricing, settlement semantics, and fees match
  BTX1.
- Adversarial covenants. BTX2 does not depend on OP_VAULT, OP_CTV, CCV, or
  any not-yet-activated soft fork. The full activation watchlist in
  `BTX-mainnet-hardening.md` still applies as forward-looking work, not as
  a precondition for BTX2.

## 2. Envelope format

```
┌─────────┬──────────┬───────────────┬──────────────────────────────┐
│ MAGIC=B │ VERSION  │ RECORD_COUNT  │ RECORDS                      │
│ T X 2   │ (u8 = 2) │ (u16 BE)      │ [ TYPE | LEN | PAYLOAD ] ... │
│ 4 bytes │ 1 byte   │ 2 bytes       │ 1+2+LEN per record           │
└─────────┴──────────┴───────────────┴──────────────────────────────┘
```

| Field | Size | Encoding | Notes |
|---|---:|---|---|
| MAGIC | 4 B | ASCII `BTX2` (hex `42 54 58 32`) | Distinguishable from BTX1 magic `BTX1` at the magic byte. Indexers MUST switch parser on magic. |
| VERSION | 1 B | u8 | Current value `0x02`. Future revisions bump this. Indexers MUST reject envelopes with unknown VERSION. |
| RECORD_COUNT | 2 B | u16 big-endian | Number of records in this envelope. 0 is legal (empty BTX2 envelope, useful for testing parser strictness). Max 65535. |
| RECORDS | variable | sequence of `(TYPE, LEN, PAYLOAD)` triples | See §3. |

Each record:

| Field | Size | Encoding |
|---|---:|---|
| TYPE | 1 B | u8 — see §3 |
| LEN | 2 B | u16 big-endian, length of PAYLOAD only |
| PAYLOAD | LEN bytes | record-specific format |

Total envelope size is at least `4 + 1 + 2 = 7 bytes` (the empty envelope)
and limited by the carrier (OP_RETURN datacarriersize on the publishing
node, or the tapscript chunk limits for the witness carrier).

A BTX2 indexer MUST:

1. Verify MAGIC is `BTX2`. If not, hand off to BTX1 parser if MAGIC is
   `BTX1`, else ignore the envelope.
2. Verify VERSION matches a known version. Unknown VERSION → ignore the
   envelope (forward-compatible).
3. Iterate records. If a record's TYPE is unknown, the indexer MAY skip
   that record but MUST continue parsing subsequent records (forward-
   compatible per-record).
4. Reject envelopes with trailing bytes after the last record.

## 3. Record types

| TYPE | Name | §  | Use |
|---:|---|---|---|
| `0x01` | SINGLE_ORDER | §3.1 | One maker order; same semantics as a BTX1 envelope. |
| `0x02` | BATCH_ANNOUNCE | §3.2 | N maker orders sharing one half-aggregate signature. |
| `0x03` | CONDITIONAL_ORDER | §3.3 | One maker order whose maker signature is an adaptor sig over an oracle's encryption point. |
| `0x04 — 0x7F` | reserved | — | Future record types. Indexers MUST skip unknown TYPEs. |
| `0x80 — 0xFF` | application | — | Reserved for application extensions. Out of scope here. |

### 3.1 SINGLE_ORDER (`0x01`)

Carries one maker order with one maker signature. The PAYLOAD is the
BTX1-compatible order body (sans magic, sans envelope wrapper) — same
field-for-field layout as `btx_0b.serialize_artifact` from version `0x02`
onward.

The maker signature in this record SHOULD be a 64-byte BIP340 Schnorr
signature (rather than the BTX1 ECDSA signature) when the maker uses a
Taproot key. ECDSA signatures remain accepted for back-compat — the
`sighash_flag` byte disambiguates per the BTX1 convention.

### 3.2 BATCH_ANNOUNCE (`0x02`)

Carries N maker orders that share a single half-aggregate signature
covering all N (pubkey, sighash) pairs.

Payload layout:

```
┌─────────┬──────────────────────────┬─────────────────────┐
│ N (u16) │ N × (BLEN | BODY)        │ HALFAGG_SIG         │
│  2 B    │ 2 + BLEN bytes per order │ 32 × (N + 1) bytes  │
└─────────┴──────────────────────────┴─────────────────────┘
```

| Field | Size | Encoding |
|---|---:|---|
| `N` | 2 B | u16 big-endian, number of orders in this batch. N ≥ 1. |
| Per-order BLEN | 2 B | u16 big-endian, length of the following BODY only. |
| Per-order BODY | BLEN bytes | Order body as in §3.4, **sans maker signature**. The 32-byte x-only maker pubkey is the trailing 32 B of BODY (for predictable indexer extraction). |
| HALFAGG_SIG | 32(N+1) B | Schnorr half-aggregate signature per §4.3 covering all N (pubkey_i, sighash_i) pairs. |

The sighash for each order is `TaggedHash("BTX2/order/sighash", BODY_i)` —
i.e., a binding of BODY_i alone (which includes the maker's own pubkey),
not of the surrounding batch. This means each maker's contribution is
independently verifiable.

A BTX2 indexer that observes a BATCH_ANNOUNCE:

1. Parses N and the N bodies.
2. For each body, computes `sighash_i = TaggedHash("BTX2/order/sighash", BODY_i)`
   and extracts the trailing 32 B as `maker_pubkey_i`.
3. Verifies the half-aggregate signature over all (maker_pubkey_i, sighash_i).
4. If verify passes, **all N orders go OPEN simultaneously**.
5. If verify fails, the entire batch is rejected; no individual order opens.

This atomicity matters: it means an honest maker cannot have one of its
batch-orders accepted while another is rejected. Batches are
all-or-nothing.

### 3.3 CONDITIONAL_ORDER (`0x03`)

Carries one maker order whose signature is an adaptor pre-signature locked
to an oracle's encryption point T. When the oracle reveals t such that
T = t·G, anyone can decrypt the pre-sig to a normal Schnorr sig that
authorizes the swap.

Payload layout:

```
┌──────────┬─────────────┬────────┬─────────────────┐
│ BLEN (u16)│ BODY        │ T (33B)│ ADAPTOR_SIG     │
│  2 B     │ BLEN bytes  │ 33 B   │ 65 B            │
└──────────┴─────────────┴────────┴─────────────────┘
```

| Field | Size | Encoding |
|---|---:|---|
| BLEN | 2 B | u16 BE, length of BODY only |
| BODY | BLEN B | Same layout as a SINGLE_ORDER body, sans maker signature. The trailing 32 B is the maker's x-only pubkey. |
| T | 33 B | Compressed encoding of the oracle's encryption point. |
| ADAPTOR_SIG | 65 B | 33 B compressed `R̂` + 32 B `s_a` per §4.2. |

The sighash that the adaptor sig is bound to is
`TaggedHash("BTX2/order/sighash", BODY)`.

A BTX2 indexer that observes a CONDITIONAL_ORDER:

1. Parses BODY, T, ADAPTOR_SIG.
2. Computes sighash and extracts maker_pubkey from BODY.
3. Calls `adaptor.pre_verify(ADAPTOR_SIG, maker_pubkey, sighash, T)`.
4. If verify passes, the order goes into a new `CONDITIONAL` state
   (distinct from `OPEN`). The indexer also records the oracle's
   encryption point T as part of the order metadata.
5. Settlement: when the indexer observes an on-chain spend of the offer
   UTXO **that contains a valid completed signature** (Schnorr sig over
   the same sighash + maker_pubkey), the indexer derives the secret t via
   `adaptor.recover(ADAPTOR_SIG, completed_sig)` and marks the order
   FILLED. The recovered t is logged with the fill (it's the oracle's
   attestation and is the cross-chain unlock secret if any).

A CONDITIONAL_ORDER can also be cancelled via the maker spending the
offer UTXO directly (standard BTX1 cancellation semantics carry over).

### 3.4 Order body layout (used by `0x01`, `0x02`, `0x03`)

All record types reference the same canonical order body, modulo whether
the maker signature is appended (`0x01`), half-aggregated externally
(`0x02`), or replaced by an adaptor sig (`0x03`).

```
struct OrderBody {
    rune_block:        u32 BE     // 4 B
    rune_tx:           u16 BE     // 2 B
    amount:            u64 BE     // 8 B
    price:             u64 BE     // 8 B (sats / unit)
    expiry:            u32 BE     // 4 B (block height)
    offer_txid:        bytes32    // 32 B
    offer_vout:        u32 BE     // 4 B
    payout_spk_len:    u16 BE     // 2 B
    payout_spk:        bytes      // payout_spk_len bytes
    maker_pubkey:      bytes32    // 32 B x-only Schnorr pubkey
}
```

Total: `64 + payout_spk_len + 32 = 96 + payout_spk_len` bytes. For a
standard P2WPKH payout (22 B spk), that's 118 B.

Three differences from BTX1:

- **Endianness:** BTX2 uses big-endian throughout (matches Bitcoin's
  network byte order and avoids the endianness ambiguity that bit a
  Codex review of BTX1 last month).
- **Maker pubkey is 32 B x-only**, not 33 B compressed. Aligns with BIP340
  Schnorr keys and is what KeyAgg outputs.
- **No sighash_flag, no embedded sig.** SINGLE_ORDER appends the sig
  separately; BATCH_ANNOUNCE and CONDITIONAL carry their sigs separately
  as documented above.

For BTX1 → BTX2 migration, see §7.

## 4. Cryptographic primitives

### 4.1 Schnorr signatures

All BTX2 signatures are BIP340 Schnorr (`btx_taproot.schnorr_sign`,
`btx_taproot.schnorr_verify`). 64-byte signatures over 32-byte sighashes.
Pubkeys are 32-byte x-only.

For SINGLE_ORDER signed by a vanilla maker key, the signature directly
follows the body. For an order signed by a maker pool (per §5), the
"vanilla maker key" is the MuSig2 KeyAgg output, and the on-chain
signature is indistinguishable from a single-signer signature.

### 4.2 Adaptor signatures

Schnorr adaptor pre-signature per `btx_adaptor.py`:

```
pre_sign(seckey, msg, T):
  R̂ = k·G + T
  e = TaggedHash("BIP0340/challenge", x(R̂) || x(P) || msg)
  s_a = (k + e·d) mod N
  pre-sig = (compressed(R̂), s_a)  → 33 + 32 = 65 bytes

pre_verify(pre-sig, P_xonly, msg, T):
  parse R̂ from compressed encoding
  e = TaggedHash("BIP0340/challenge", x(R̂) || P_xonly || msg)
  check  s_a·G + T == R̂ + e·lift_x(P_xonly)

decrypt(pre-sig, t):
  s = (s_a + t) mod N
  completed-sig = (compressed(R̂), s)  → 65 bytes

recover(pre-sig, completed-sig):
  t = (s - s_a) mod N
```

### 4.3 Half-aggregate Schnorr signatures

Per `btx_halfagg.py`, following BlockstreamResearch/secp256k1-zkp's
`schnorrsig_halfagg` module:

```
aggregate(pubkeys, msgs, sigs):
  N = len(pubkeys)
  aggsig = R_0 || R_1 || ... || R_{N-1} || s
  where  s = sum_i z_i · s_i  mod N
        z_0 = 1
        z_i (i ≥ 1) = TaggedHash("HalfAgg/randomizer",
                                  R_0||pk_0||m_0||...||R_i||pk_i||m_i) mod N
  Size: 32 · (N + 1) bytes.

verify(pubkeys, msgs, aggsig):
  parse R_0..R_{N-1}, s from aggsig
  for each i: compute e_i = TaggedHash("BIP0340/challenge", R_i||pk_i||m_i)
             compute z_i (as above)
  check  s·G == sum_i z_i · (R_i + e_i · pubkey_i)
```

### 4.4 MuSig2 KeyAgg

Per `btx_musig2.py`, following BIP327 §3:

```
key_agg(pubkeys_xonly):
  L = TaggedHash("KeyAgg list", X_1 || X_2 || ... || X_n)
  second = the first pk in the list distinct from pk[0]
           (None if all pubkeys are equal)
  for each pubkey i:
    a_i = 1 if pubkey_i == second
        = TaggedHash("KeyAgg coefficient", L || pubkey_i) mod N
        otherwise
  Q_raw = sum_i a_i · lift_x(pubkey_i)
  if Q_raw has even y: Q = Q_raw, gacc = +1
  else:                 Q = -Q_raw, gacc = -1
  return aggregated_pubkey_xonly = x(Q), coefficients, gacc, L, second
```

The signing protocol used by the maker pool is the standard BIP327 2-round
interactive protocol. For production deployment, BTX2 implementations
MUST use a vetted MuSig2 signing library (rust-secp256k1-zkp's musig
module, or a binding thereof). The `pool_sign_demo()` function in
`btx_musig2.py` is a research-only trusted-aggregator path and is NOT
suitable for production maker-pool deployment.

## 5. Maker pools

A maker pool consists of N participants who collectively control a set of
offer UTXOs and publish BTX2 orders that appear on-chain to be signed by
a single maker.

Setup (one-time):

1. The N participants exchange pubkeys out-of-band.
2. They agree on a canonical pubkey order (e.g., lexicographic sort).
3. They each compute `key_agg(pubkeys_xonly)` and verify they all derive
   the same `aggregated_pubkey_xonly`. This is the **pool pubkey**.
4. They use the pool pubkey as the destination for offer UTXOs (P2TR
   addresses derived from the pool pubkey via standard Taproot tweaking,
   or P2WPKH addresses derived from the pool pubkey via standard
   `Hash160` — depending on the offer mechanics).

Per-offer (each time the pool publishes):

1. The pool members agree on the order body (rune, amount, price, etc.).
2. Each member generates round-1 MuSig2 nonces and shares them.
3. Each member produces a round-2 partial signature.
4. A designated aggregator combines the partials into one 64-byte
   Schnorr signature.
5. The aggregator publishes the BTX2 SINGLE_ORDER record with the pool's
   aggregated pubkey as the maker_pubkey field and the combined signature.

Indexer experience: the indexer sees a vanilla SINGLE_ORDER record with
a 32-byte maker_pubkey and a 64-byte Schnorr sig. It cannot tell whether
the order is from a single maker or a pool. This is by design — maker
pool participation is private at the chain layer.

**Security note (rogue-key defense).** The BIP327 KeyAgg algorithm
includes a defense against rogue-key attacks where one participant chooses
their pubkey based on others' pubkeys. The defense relies on the "second
key" rule and the coefficient hash. Implementations MUST follow BIP327's
KeyAgg algorithm faithfully; ad-hoc key aggregation (e.g., naive sum of
pubkeys) is vulnerable.

## 6. Conditional / oracle-attested orders

A CONDITIONAL_ORDER lets a maker publish an offer that only settles if a
specific oracle attests a specific outcome. The mechanism uses Schnorr
adaptor signatures.

Use cases:

1. **DLC-style conditional spot orders.** "I'll sell this rune for these
   sats IF oracle O signs Y by block H." The encryption point T is the
   oracle's expected attestation point for outcome Y; t is the oracle's
   secret it reveals on attestation.

2. **Cross-chain atomic swap building block.** "I'll fulfill this swap
   when the counterparty completes a Lightning payment." The encryption
   point T is the Lightning payment's HTLC/PTLC point; revealing the
   preimage completes both legs.

3. **Order privacy.** A maker can pre-encrypt their order signature to
   a key only a specific taker can derive (e.g., after sending a fee
   deposit). The CONDITIONAL_ORDER is broadcast; nobody else can decrypt
   to spend the offer until they've satisfied the maker's encryption
   condition. Generalizes the "addressed mode" snipe-resistance from
   BTX1.

A conditional order is in `CONDITIONAL` state from announce until either:

- The maker spends the offer UTXO (→ CANCELLED).
- The oracle attests and a settlement tx is observed (→ FILLED, with the
  recovered t logged).
- The order's expiry height passes (→ EXPIRED).

The indexer state machine for CONDITIONAL orders is one additional state
on top of the BTX1 state machine. Standard BTX1 OPEN/FILLED/CANCELLED/
EXPIRED states remain unchanged for SINGLE_ORDER and BATCH_ANNOUNCE
records.

## 7. Migration from BTX1

**Coexistence period.** Indexers SHOULD support both BTX1 and BTX2
envelopes during the migration. The two formats use distinct magic bytes
(`BTX1` vs `BTX2`), making dispatch unambiguous.

**Recommended timeline:**

- **Phase 1 (any time after this spec freezes):** BTX2-capable indexers
  ship. Indexers serve a combined book that contains both BTX1 and BTX2
  orders. Makers continue to publish BTX1 by default.
- **Phase 2:** Makers begin publishing BTX2 SINGLE_ORDER for new orders.
  BTX1 orders continue to settle normally. BTX2 batch and conditional
  records appear when makers / makers-pools opt in.
- **Phase 3 (proposal: ≥6 months after Phase 1):** BTX1 publishing is
  deprecated. Indexers continue to read existing BTX1 orders from chain
  but emit a deprecation warning when an indexer is fed a fresh BTX1
  announcement. BTX1 indexer code remains for historical reconstruction.
- **Phase 4 (proposal: ≥12 months after Phase 1):** BTX1 publishing is
  no longer supported by reference implementations. BTX1 historical
  records remain readable; BTX1 announcement is a soft-warning.

**On-chain compatibility.** BTX2 envelopes use a different MAGIC, so they
are inherently distinguishable from BTX1. Carrier mechanics (OP_RETURN
or Taproot witness envelope) are unchanged.

## 8. Byte budget

Measurements from `btx_artifact_v2_demo.py` for a standard P2WPKH-payout
maker order, comparing BTX1 (N independent envelopes) to BTX2 (one
envelope wrapping one BATCH_ANNOUNCE record of N orders):

| N | BTX1 total | BTX2 total | Savings |
|---:|---:|---:|---:|
| 1 | 207 B | 196 B | 5.3% |
| 5 | 1,035 B | 804 B | 22.3% |
| 10 | 2,070 B | 1,564 B | 24.4% |
| 20 | 4,140 B | 3,084 B | 25.5% |
| 50 | 10,350 B | 7,644 B | 26.1% |

The savings plateau at ~26%. The raw signature compression (half-agg
math) is 45-50%, but signatures are only ~30% of the artifact; the
remaining ~70% is order bodies (txid, pubkey, amounts, payout spk),
which BTX2 doesn't compress.

For CONDITIONAL_ORDER vs an equivalent BTX1 announce, the size is
roughly the same: BTX2 adds 33 B (encryption point T) but the adaptor
sig is the same size as a regular Schnorr sig + sighash byte.

## 9. Security considerations

### 9.1 ECDH leakage from adaptor signatures

The C reference (`secp256k1-zkp/src/modules/ecdsa_adaptor`) ships with a
prominent warning:

> the adaptor signature leaks the Elliptic-curve Diffie–Hellman (ECDH)
> key between the signing key and the encryption key.

Concretely: given signing pubkey `P = d·G`, encryption pubkey `T = t·G`,
and the adaptor signature, anyone can compute `T^d = P^t`. This is a
problem if the same signing key `d` is used in protocols that rely on
the hardness of the CDH problem (Diffie-Hellman key exchange, ElGamal
encryption, Lightning gossip's noise handshake, etc.).

**BTX2 mitigation:** BTX makers SHOULD use fresh keys per offer for
CONDITIONAL_ORDER. BTX1 already creates a fresh keypair per signing
session, so the existing maker-side practice carries through. The threat
applies if a maker key is **reused** across BTX adaptor sigs and an
unrelated DH-based protocol.

**Implementer requirement:** any BTX2 reference implementation that
exposes adaptor-sig signing MUST document this warning prominently in
its CONDITIONAL_ORDER API. Pull requests adding adaptor-sig support to
indexers SHOULD include a check or warning that the same maker pubkey
isn't observed signing both an adaptor sig and a regular sig (which
would indicate key reuse across adaptor-sig and non-adaptor contexts).

### 9.2 MuSig2 nonce handling

BIP327's 2-round signing protocol is exquisitely sensitive to round-1
nonce handling:

- Reusing a round-1 nonce across signing sessions leaks the maker's
  share of the secret.
- Leaking a partial signature before the full session completes leaks
  the secret.
- The two-nonce structure (one per signer per session, generated as
  `(R1_i, R2_i)` and combined into the aggregate nonce) exists
  specifically to defeat concurrent-signing attacks; weakening to
  one-nonce-per-signer breaks the security proof.

**Production requirement:** BTX2 maker-pool deployments MUST use a
vetted MuSig2 implementation (`rust-secp256k1-zkp/src/modules/musig` via
Rust bindings, or the experimental Python `musig2` crate that wraps the
C reference). The `pool_sign_demo()` function in `btx_musig2.py` is
explicitly NOT suitable for production.

### 9.3 Indexer state-machine determinism

For a CONDITIONAL_ORDER to transition CONDITIONAL → FILLED, the indexer
must observe a settlement transaction that contains a valid completed
signature. The recovered secret `t` is then logged.

Implementers MUST ensure:

- The completed signature is verified against the same maker_pubkey +
  sighash as the original adaptor sig (i.e., that the on-chain spend
  was authorized by the same maker, not a third party who happened to
  spend the offer UTXO with a different sig).
- The recovered `t` matches the announced encryption point: `t·G == T`.
  If not, the state transition is rejected and the order stays
  CONDITIONAL (this prevents an attacker from publishing an unrelated
  valid sig and claiming it settled a conditional order).

### 9.4 Format-versioning hazards

The VERSION byte must be checked. A v3 BTX envelope MUST NOT be parsed
as v2 — that would be a downgrade attack vector. Implementations that
encounter VERSION != known MUST ignore the envelope.

The Python implementations are the reference. A Rust port into `brk-btx`

verification path must be implementable in the production indexer). The
Rust port should mirror the Python module structure: `halfagg.rs`,
`adaptor.rs`, `musig2.rs`, and a v2 envelope parser alongside the
existing v1 parser at `brk_indexer/src/btx.rs`.

## 11. Open questions

- **Maker pubkey rotation.** Should a CONDITIONAL_ORDER's maker pubkey
  be allowed to differ from the offer UTXO's authorizing key? (BTX1
  enforces equality via `verify_maker_sig`'s P2WPKH binding.) For BTX2,
  the cleanest answer is "still equal — the adaptor sig is over the
  same sighash that the standard offer-UTXO spend authorizes." Pending
  threat-model review.
- **Half-agg with mixed Schnorr / ECDSA.** A BATCH_ANNOUNCE today
  requires all N maker sigs to be Schnorr (half-agg is Schnorr-only).
  Should we allow heterogeneous batches with some Schnorr + some ECDSA
  sigs? Probably no — the savings disappear. Recommend: BTX2 BATCH_ANNOUNCE
  is Schnorr-only, full stop.
- **Conditional orders with multi-oracle attestation.** A k-of-N oracle
  set can be expressed via FROST (RFC 9591) — not in this spec yet, and
  not yet in `secp256k1-zkp`. Out of scope for BTX2 v1.

### 11.x Decisions 2026-06-04 (post-Rust-port closure)

Three open questions about the multi-round MuSig2 surface — surfaced by
the consumer-survey memo `BTX-musig2-multiround-consumer-survey-2026-06-04.md`
after the Rust verification port shipped at brk-btx commit `60ebb51` —
are recorded here as **closed**. Full rationale in
`BTX-musig2-multiround-consumer-DECISIONS-2026-06-04.md`.

| Question | Decision | One-line reason |
| -------- | -------- | --------------- |
| Multi-org maker pools | **YES** | Zero on-chain cost; matches BTX's competitive benchmark (Light Pools); liquidity case is clear |
| Slashing in v1 | **NO**, defer to post-covenant | Needs covenants Bitcoin doesn't have; MuSig2 fail-stop suffices; no consumer asks for it |
| Rust pool aggregators | **YES (optionality), defer signing port** | Verification half ships; signing port written only when a real Rust aggregator service needs it |

These decisions touch §5 (Maker pools) and §9.2 (Nonce handling) only in
the sense that they confirm the existing text is correct under the
chosen direction. No edits to §5 / §9.2 / §10 are warranted.
